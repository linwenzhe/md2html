# 与 AI 高效协作的提问经验总结

**——以「Markdown 转 HTML 工具」项目为例，写给不熟悉 AI 的人**

---

## 一、这份文档适合谁

如果你刚接触 AI 对话工具，不知道怎么提问、怎么让 AI 帮你写程序、怎么写文档、怎么一步步把想法变成可交付的成果，这份文档就是为你准备的。

它不教具体技术，而是总结一套**和 AI 协作的提问方法**。方法来自一个真实项目：从“Markdown 怎么渲染”开始，到最后交付一个可运行的 Python 工具、JSON 配置文件、完整 README 文档，并让 README 能被程序自己转成 HTML。

---

## 二、一句话核心

**不要把 AI 当搜索引擎，要把它当结对编程的伙伴。**

好的协作方式不是“一句话让 AI 干完所有事”，而是：

> **先问方向 → 再做最小实现 → 逐步加约束 → 主动查边界 → 要求文档化 → 最后按交付件整理。**

---

## 三、本项目的提问路线图

下表把整个项目拆成 14 个阶段。左侧是提问者的原话（或大意），右侧是这一步在做什么、用了什么技巧。

| 阶段 | 提问大意 | 目的 | 可学习的技巧 |
|---|---|---|---|
| 1. 探索原理 | “markdown格式是一种很好的格式，可以通过简单语法实现格式化文本。目前主流方案，如何实现从md源码到渲染出预览结果呢” | 先建立技术地图，不急着写代码 | 先问“有哪些主流方案”，再问“帮我实现” |
| 2. 最小实现 | “能否实现一个py程序，输入markdown文档，输出html文件？” | 明确语言、输入、输出 | 一句话说清：语言 + 输入 + 输出 |
| 3. 配置化 | “我希望这个 py 程序可以通过 json 文件配置输入输出的文件名。” | 把硬编码变成可配置 | 一次只加一个主要约束 |
| 4. 边界确认 | “如果原本的 md 文档有引用图片，生成的 html 文件内正常展示吗？” | 提前暴露风险 | 主动问“如果……会怎样？” |
| 5. 概念澄清 | “base64 内嵌是类似 mhtml 文件的实现吗？” “data.js 呢？” | 比较不同方案 | 用已知概念类比新概念，短追问 |
| 6. 功能选项 | “在json文件中设置一个选项，让用户自己选择生成的html，用哪种方式实现，可选参数是[1，不展示图片，2，引用图片(需配置html文件与图片资源的相对路径，指定一个存放图片的根目录)，3，data.js方式实现，4，Bast64内嵌]” | 把选择权交给用户 | 用编号枚举，减少歧义 |
| 7. 可读性增强 | “在json中，增加一个"说明"配置，不作为程序入参，只是告诉用户如何使用程序，尤其是4种模式，入参是数字，可能造成困惑。” | 区分程序参数和文档字段 | 明确“不作为入参”这类边界 |
| 8. 交付要求 | “对于本项目，给出全部交付件，应含有:1，程序文件，使用说明(md文件)，配置文件(json)，此外，对于本项目的使用说明文档，应当能通过程序转换成html。” | 定义验收标准 | 要求文件清单 + 自举验证 |
| 9. 环境前提 | “项目说明文档是否足够详尽，如果用户环境没有Python环境，至少要告知用户如何简要配置环境，添加项目依赖等。” | 补全前提条件 | 让 AI 检查“文档是否足够详尽” |
| 10. 结构主次 | “环境配置说明只是简要补充，没必要放在文档最前面，要有主次，但是，考虑到环境配置是前提条件，可以在前面做一个"章节跳转或章节指示"。” | 调整信息架构 | 不满意结构时，给明确调整规则 |
| 11. 附录扩展 | “附录中拓展一下，简单介绍 md 的常见语法。” | 完善辅助知识 | 要求“简单介绍”，控制篇幅 |
| 12. 重新整理 | “按照项目交付要求，重新整理，把项目文件发给我。” | 收敛为最终产物 | 要求完整交付，不要碎片 |
| 13. 元总结 | “从本项目开始到结束，整个过程，我的提问方式，你能否总结出一份文档(md)，我希望可以把这个经验分享给一个不熟悉ai使用的人员，让他能够从中学习到与ai交流的技巧。” | 沉淀经验 | 让 AI 复盘协作过程 |
| 14. 元总结 | “实现md转html，这个项目有什么价值，总结一下，输出一份md文档” | 沉淀价值 | 让 AI 复盘项目价值 |

## 四、从案例中提炼的 10 个技巧

### 1. 先问“有哪些方案”，再问“帮我实现”

一开始不要直接说“写个 Markdown 转 HTML 程序”。先问：

> “目前主流方案有哪些？各自优缺点是什么？”

这样你能知道 `marked`、`markdown-it`、`remark`、`Python-Markdown` 等选项，再决定用哪个。**先地图，后路径。**

### 2. 一句话说清：语言 + 输入 + 输出

好的第一句需求：

> “能否实现一个 py 程序，输入 markdown 文档，输出 html 文件？”

它同时包含了：
- 语言：Python
- 输入：Markdown 文档
- 输出：HTML 文件

AI 立刻能给出可运行代码。

### 3. 一次只加一个主要约束

不要一口气说：

> “要支持 JSON 配置、四种图片模式、批量处理、目录、高亮、还要文档自举……”

而是先让它能跑，再加配置，再加图片模式，再加文档。**每次只加一个维度**，出错容易定位。

### 4. 主动问边界：“如果……会怎样？”

项目中途问：

> “如果原本的 md 文档有引用图片，生成的 html 文件内正常展示吗？”

这个问题提前暴露了相对路径、Base64、data.js、MHTML 等关键设计。**边界问题越早问，返工越少。**

### 5. 用枚举和编号，消灭模糊

> “可选参数是 [1,2,3,4]：1 不展示图片，2 引用图片，3 data.js，4 Base64 内嵌。”

数字 + 含义一起给，AI 不会猜错。**能用表格、编号、枚举，就不要用“大概”“可能”“你看着办”。**

### 6. 区分“程序参数”和“文档字段”

> “增加一个‘说明’配置，不作为程序入参，只是告诉用户如何使用。”

这句话非常关键。它告诉 AI：
- 这个字段要写进 JSON
- 但程序不能读它、不能拿它当参数
- 它的唯一作用是给人看

**边界越清晰，AI 越不容易混淆。**

### 7. 要求“全部交付件”，而不是只给代码

> “给出全部交付件，应含有：程序文件、使用说明（md）、配置文件（json）。”

这相当于给 AI 一个验收清单。最终产物就完整了：`md2html.py`、`config.json`、`README.md`、`dist/`。

### 8. 要求“自举验证”

> “对于本项目的使用说明文档，应当能通过程序转换成 html。”

这叫自举：用项目自己的工具处理自己的文档。它同时验证了：
- 程序能跑
- 配置正确
- 文档格式兼容
- 输出结果可用

**要求闭环验证，比“看起来对”可靠得多。**

### 9. 让 AI 当评审者，检查遗漏

> “项目说明文档是否足够详尽，如果用户环境没有 Python 环境，至少要告知如何配置环境、添加依赖。”

这是让 AI 从“生成者”切换成“评审者”。它会主动列出缺口，再补全。**你可以经常问：“还缺什么？”“如果我是新手，哪里会卡住？”**

### 10. 不满意结构时，给明确调整规则

> “环境配置只是简要补充，没必要放在文档最前面，要有主次，但前面可以做章节跳转。”

不要只说“重写”。要告诉 AI：
- 什么放前面
- 什么放附录
- 用什么方式导航（章节跳转、锚点）
- 主次关系是什么

**结构问题，用结构指令解决。**

## 五、可直接照抄的提问模板

### 模板 1：探索方案

```text
我想做 [目标]。请先不要写代码，先给我 3 种主流方案，
列出各自优缺点、适用场景和依赖，最后给一个推荐。
```

### 模板 2：最小实现

```text
请基于 [方案] 实现一个最小可运行版本。
语言：[Python/JS/...]
输入：[...]
输出：[...]
依赖：[...]
要求：代码完整，可直接运行，并给出运行命令。
```

### 模板 3：增加配置

```text
请把 [某个硬编码项] 改成通过 [JSON/YAML/环境变量] 配置。
配置字段包括：[字段1]、[字段2]。
给出配置示例和默认值。
```

### 模板 4：边界确认

```text
如果出现 [某种情况]，结果会怎样？
请列出可能的问题、原因和解决方案。
```

### 模板 5：功能选项

```text
请在配置中增加一个选项，让用户选择 [功能] 的实现方式。
可选值：
1 = [...]
2 = [...]
3 = [...]
4 = [...]
默认值用 [X]。
```

### 模板 6：文档化

```text
请为这个项目写一份 README。
读者是 [新手/开发者/运维]。
必须包含：安装、快速开始、配置字段、常见问题、依赖。
假设读者没有 [Python/Node/Docker] 环境，请补全环境准备。
```

### 模板 7：让 AI 自检

```text
请检查这份文档是否足够详尽。
列出 3 个最可能让新手卡住的点，并补全。
```

### 模板 8：最终交付

```text
请按项目交付要求重新整理，把全部文件发给我。
交付件包括：[文件1]、[文件2]、[文件3]。
并给出验证步骤。
```

### 模板 9：经验总结

```text
请总结我们这次对话中我的提问方式，
写成一份给不熟悉 AI 的人看的经验文档。
```

## 六、新手常见误区

| 误区 | 更好的做法 |
|---|---|
| “帮我写个程序。” | 说清语言、输入、输出、依赖 |
| 一次提 10 个需求 | 一次只加一个主要约束 |
| 不说运行环境 | 提前说明操作系统、Python 版本、是否联网 |
| 只说“不对”，不说哪里不对 | 贴报错、贴期望结果、贴实际结果 |
| 让 AI 重写整个项目 | 指明要改的文件、函数、行为 |
| 不要求文档 | 明确要 README、配置说明、常见问题 |
| 不验证 | 要求给运行命令和验证步骤 |
| 把 AI 当搜索引擎 | 把它当结对伙伴，持续追问、迭代 |

## 七、一页纸速查表

**每次提问前，问自己 5 个问题：**

1. **目标**：我到底想要什么？
2. **输入**：我给 AI 什么材料？
3. **输出**：我要它产出什么格式？
4. **约束**：语言、版本、依赖、不能做什么？
5. **验收**：怎么判断它做对了？

**每次 AI 回答后，问自己 3 个问题：**

1. 这一步能运行吗？怎么验证？
2. 还缺什么边界情况？
3. 下一步只加哪一个约束？

**推荐句式：**

- “请先不要写代码，先比较方案。”
- “请给出最小可运行版本。”
- “如果……会怎样？”
- “请把配置项列成表格。”
- “请补全文档，假设用户没有环境。”
- “请按交付件重新整理。”
- “请总结我的提问方式。”

## 八、结语

这个项目最后能交付 `md2html.py`、`config.json`、`README.md` 和自举生成的 `dist/README.html`，不是因为某一次提问特别完美，而是因为提问者一直在做三件事：

1. **逐步加约束**：从最小实现到配置化，再到四种图片模式。
2. **主动查边界**：图片、路径、环境、结构、主次，都提前问清楚。
3. **要求可交付**：不只给代码，还要文档、配置、验证和最终整理。

把这套方法用在任何 AI 对话里，你都会得到更稳定、更完整、更可用的结果。

**记住：AI 不会读心，但它非常擅长在你给出清晰目标、输入、输出、约束和验收标准后，帮你把想法变成现实。**
